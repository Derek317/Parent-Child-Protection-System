# IG Guard 6.0.2 — fixes from an audit of 6.0

Documented: **26 November 2026 (Hong Kong)**. Bundled Terms revision: `2026-11-26-v9`. Earlier version: [6.0](6.0.md). Later version: [6.0.3](6.0.3.md). No version 6.0.1 was released; its one fix is part of this version.

Tag and version name `6.0.2`. Version code: 100 plus the GitHub Actions run number of the release run; the installed app shows it. It installs over 6.0 and keeps the pairing and data, because it is signed with the same key.

6.0.2 is 6.0 with the fixes below. Everything in the [6.0 release notes](6.0.md), including the open risks, still applies unless this page says otherwise. These notes do not claim legal clearance, Meta approval, reliable detection of grooming or an absence of defects or vulnerabilities. ## What changed

**Instagram export import (manual upload)**

- **Who the teen is.** In an export, each conversation folder is named after the other person, followed by a number. The app reads that first: in a two-person chat the one matching the folder is the other person, and the remaining one is the teen. The child is not asked to type their account name. If no folder can be matched (for example names not written in Latin letters), the app falls back to the stored handle, then to the person who appears in the most chats.
- **A group the teen never wrote in** no longer stops the import. Groups are still set aside and not scored.
- **A chat the teen never answered** is now scored as a one-to-one chat, all incoming. Before, it was set aside like a group.
- **Messages older than 14 days are dropped while the file is read**, so a large old export is no longer refused. The limits against hostile archives (size of one file, number of entries, total unpacked size, paths) are unchanged.
- **The same message is stored once** whether it comes from a JSON or an HTML export or an export in another language.
- **A conversation is identified by Instagram's own thread number**, so two accounts with the same name are two conversations, and a changed display name is still the same conversation.
- **A repeated import keeps one conversation and one score.** A conversation's score is still the highest of the last 14 days. After an import that overlaps a stored conversation, a new score that is equal or higher replaces the earlier ones; a lower one, or an attempt that gives no score, leaves the earlier score until it ages out.

**Keys, release and delivery**

- **A key rotation reaches a child phone that was offline for days.** The command stays valid for up to 10 days (3 days on the parent phone plus 7 at the relay). Before, a child offline for more than 24 hours refused it and the family was split.
- **A release or remote reset stays valid for up to 10 days**, where it was 20 minutes. The child phone is released when it next comes online; until then its own screen still shows that it is monitored. The parent's screen says so. A release for an earlier pairing cannot act on a later one.
- **"Not sent" is only shown when a release never left the phone.** If the answer did not arrive in time, or the connection closed after the release was handed to it, the parent is told "sent, not confirmed" and the release stays queued.
- **A child clock set ahead and then back** no longer blocks later records or pauses the records-not-delivered check.
- **A child phone whose clock runs a few minutes fast counts as running again.** Its heartbeat was ignored when dated more than 2 minutes ahead of the parent's clock, so the parent was told the child had stopped reporting. Now it is recorded at the parent's own time; one dated more than 24 hours ahead is still ignored.
- **A record queued while an older send was ending** (after a pairing, a key rotation or a capture) is sent when that send ends, where it could wait for the next regular check.
- Texts that told the parent to pair again "by invitation" now say by QR code under "加入子女 · Add a child".

**Relay**

- Each phone may create at most 30,000 new record ids per UTC day, of which ordinary data at most 10,000. A real family sends a few hundred a day. A refused record is kept on the phone and sent again later; nothing is dropped. The limit is per phone, so one phone cannot use up the other's.
- The relay's lifetime table has an index, so connecting no longer reads the whole table.

**Scoring**

- A chat whose scoring fails once is tried again at the next run. After two failures in a row at the same point it is stored as "needs review" until new messages arrive, as before.

**Build**

- The app's tests run in their own job, without secrets, and the relay deploy and the signing job wait for it. Before, the relay went live as soon as its own tests passed.

## Terms and documents

- **Terms revision `2026-11-26-v9`.** One sentence changed in each language: the Terms said that after a child clock was set ahead and back, heartbeats were not used for the records-not-delivered notice until the clock caught up. That pause no longer exists, so the sentence now says the notice goes on working once the clock is back. Nothing else in the Terms changed. Existing users see the one-time "Terms updated" notice; no new consent is asked.
- The deletion guide and the privacy policy each gained one sentence about the 10 days a release stays valid.
- Left out of the Terms on purpose: the 10-day release, the score rule after a repeated import, and the relay's daily limit. They are stated here and, for the release, on the parent's screen.

## Not fixed, and known limits

- **The parent still shows one row for two accounts with the same name**, with the higher score. They are scored separately on the child phone; the report to the parent still groups by name.
- **After upgrading from 6.0**, an import only recognises earlier messages if it uses the same format and language as before. Otherwise the earlier copies stay beside the new ones until they age out after 14 days.
- An HTML export made in another time zone than the phone's can give different message identities than JSON.
- Two same-name accounts that 6.0 had merged are split by their thread numbers; the old merged score goes to whichever is read first.
- A single message file imported after a zip of the same conversation is stored as a second conversation.
- **No real Instagram export was used.** The folder format (name, underscore, number) is taken from the app's invented test data. If a real export differs, the app falls back to the older rules.
- When a child phone accepts a key rotation, records already waiting with a retry time still wait for that time.
- A pairing message can still take about 30 seconds when its first attempt fails; an automated test that waits 20 seconds fails now and then, and the cause is not established. The test now prints the state when it happens.
- **Found by a second audit, present since 6.0 or earlier, fixed in 6.0.3 and not here:**
  - The records-not-delivered warning can come early: one bad heartbeat hours after an earlier one can raise it at once.
  - A second import while scoring is running is scored at the next overnight charge, not straight away.
  - A large import is slow on a heavy account, and heartbeats can be delayed while it runs (a missing database index).
  - A multi-part record that is complete but refused keeps its parts for up to 3 days; after about 100 of them, new large records are refused until they expire.
  - Retiring a pairing room can hold up sending and receiving for up to 15 seconds each on a slow network.
  - The password check freezes the unlock page and the role-change sheet for about 2 seconds on a slow phone.
  - If the app is killed while the parent's signing key is first created, "加入子女 · Add a child" crashes. The way out is to leave the parent role and set up again.
  - A child record that arrives again, or late, can set the child's own account name on the parent phone back to an older one.
  - A list of relay delivery numbers is kept that never catches a repeat (each kind of record has its own repeat check) and slows each incoming message a little.
  - About 250 lines of unused code are still in the app.
  - A hotfix tag other than `4.8-hotfix.N` does not deploy the relay.
