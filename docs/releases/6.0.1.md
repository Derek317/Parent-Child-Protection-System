# IG Guard 6.0.1 — delivery timing fix

Documented: **25 November 2026 (Hong Kong)**. Bundled Terms revision: `2026-11-24-v8`, unchanged. Earlier version: [6.0](6.0.md).

Tag and version name `6.0.1`. Version code: 100 plus the GitHub Actions run number of the release run; the installed app shows it. It installs over 6.0 and keeps the pairing and data, because it is signed with the same key.

6.0.1 is 6.0 with one fix. Everything in the [6.0 release notes](6.0.md), including the open risks and what was and was not tested, still applies. These notes do not claim legal clearance, Meta approval, reliable detection of grooming or an absence of defects or vulnerabilities.

## What changed

- **Fixed: a record could wait after a pairing.** Right after a pairing, a key rotation or a reset, a record queued for the new family could stay unsent until something else started delivery again. On the parent phone that is the pairing message the child phone waits for; on the child phone it is the first record after pairing. The app sends one record at a time; if an older send was just ending at that moment, the new request to send was turned away and the ending send did not start delivery again, because the family had changed.
- **How long it could wait.** Until the next trigger: about a minute where the parent service or the child's Notification access is running, and up to about 15 minutes (the background job) on a child phone with both Android permissions off. Opening the app or the other phone coming online also ended the wait.
- **What it did not do.** No record was lost, nothing was sent to the wrong family, and no protection or warning was weakened. It was never observed on a real phone; it was found because an automated test timed out now and then.
- **The fix.** A request to send that is made right after a record was queued, and that finds a send still running, now leaves a note; when that send ends, the app sends once more. Requests from timers, screens and the connection itself are unchanged from 6.0.

- **Not changed.** When a child phone accepts a key rotation, the records it had waiting are moved to the new family without a request to send them, so they still go out at the next regular check, as in 6.0. The fix covers a pairing and records queued afterwards.

No consent step, warning, capture scope or security measure was changed. The relay code is unchanged.

## Tests and build (not part of the app)

- The Android jars the tests need now come through Gradle from Google's Maven Central mirror, each checked against a pinned SHA-512, because Maven Central rate-limited GitHub's machines.
- A failed test now prints its message.
- One test that could fail by chance on sealed text was corrected and made stricter.
- Two new tests: one reproduces the timing flaw (it fails without the fix and passes with it); the other checks that a send left over from an earlier family starts nothing by itself when it ends.
- Every test now prints its name when it starts, and the build job stops after 60 minutes.

## Tested, and not tested

Tested:

- 938 unit tests on the Windows development PC; 1 failed there, the known `RelayOutboxTest > concurrentFirstOpenCannotRaceDatabaseCreation`, which fails only on that PC. The same result with the tests limited to two processor cores.
- Lint reported 0 errors.
- The new test with the fix removed: it failed with the same message as the intermittent failures on GitHub ("M3 at the relay", nothing published). With every request leaving a note, the leftover-send test failed (three sends ended where one was expected).
- Two earlier forms of this fix were dropped before release. The first restarted delivery whenever anything was waiting when a send ended; with it, one GitHub run hung in the test step for over an hour and was cancelled. The second noted every request that found a send running, which turned out to be nearly every send. The released form is the third.

Not tested:

- The flaw itself on a real phone: it was never seen there, so there is no before-and-after check on hardware.
- Why the GitHub run hung with the first form: it was not reproduced on the development PC, also not with the tests limited to two processor cores, so the cause is not established.
- Whether the intermittent test failures on GitHub are gone for good; only further runs can show that.
- Everything listed as not tested in the [6.0 release notes](6.0.md).
