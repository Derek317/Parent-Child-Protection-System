# Local storage security — 5.0

Updated 20 November 2026 (Hong Kong). See the [release notes and known limits](releases/5.0.md).

Preference strings and captured archive content are encrypted at rest using AES-256-GCM and keys generated in Android Keystore. These keys are separate from the shared family transport secret and from the developer's APK signing identity. No database decryption key is shipped in the APK or stored in ordinary preferences. Hardware backing depends on the device; this release does not claim that every device has hardware-backed storage.

## Protected data and remaining metadata

- Preference strings include the parent master password where existing reveal/pairing functions need it, family token, verifier/configuration state, pending routine key transitions and legacy message caches. Numeric flags and preference key names remain ordinary metadata. The child stores a password verifier. This release does not claim that every password has been removed from memory or parent storage.
- Production parent-command signing uses a non-exportable EC private key in Android Keystore, separate from the local AES/HMAC keys, family transport secret and APK signing identity. Legacy private material is imported only after verifying it matches the pinned public key and can sign; the production caller then removes the encoded private-key preference. Existing child public-key trust is preserved. A mismatched established identity raises an error rather than silently generating a replacement. If moving an existing key into the Keystore fails, the app keeps using that existing key (stored encrypted by the app, not hardware-protected), shows a warning and retries at each start; the old copy is removed only after the Keystore key is verified to match the key the child trusts. A missing identity with no existing key still raises an error. Software identities and encoded-key support remain for test/protocol helpers and legacy compatibility; they are not the production storage path, except that the existing legacy key keeps working while its move into the Keystore is pending.
- Archive message bodies, original payloads, sender/conversation/account labels, fragment data and capture-window state are separately authenticated and encrypted. Purpose/record/family binding prevents ciphertext from being moved between different fields or family scopes without detection.
- Sender and conversation lookup columns use Keystore HMAC indexes. Timestamps, alert categories, directions, opaque record/family IDs and workflow flags remain clear metadata. This is field encryption in SQLite, not encryption of the complete database file.
- Keyword search decrypts candidate rows inside the app. It does not create a persistent plaintext search index. Search cost grows with the candidate archive; this is a deliberate privacy/performance tradeoff.
- The first-launch receipt is stored separately in `ig_guard_consent`, sealed with the same device-bound AES-GCM facility and a distinct authenticated purpose. It records the three acknowledgments, original Terms revision and SHA-256, app version and acceptance time. It is local and is not a relay/support upload. Normal family-setting changes and archive deletion do not remove it; clearing app data/uninstallation does. Ordinary updates preserve the original receipt rather than recording agreement to a new revision. Unreadable receipts leave capture and relay disabled and are not silently replaced.

## Parent access, clipboard and background processing

Parent records, settings and explicit copy/export controls sit behind native Android biometric/device-credential authentication. The activity relocks on leaving the foreground and dismisses its dialogs. A configured Android screen lock is required; anyone able to use the enrolled credentials may be able to unlock the app. Showing the master password, key rotation, remote reset, compromise re-pairing and leaving the parent role each require a new authentication; leaving the parent role removes the master password and signing key. Temporary-unlock and lockout timers use the monotonic clock plus a boot marker, so changing the wall clock cannot extend them. Secure-window flags request screenshot/preview protection, and notifications use generic content with a private visibility/public fallback. These controls depend on Android and device behavior and do not protect a compromised running process.

UI authorization is separate from transport and signing. Background reception, decryption, archiving, signed receipts and eligible queued delivery do not require the parent screen to remain unlocked. Signing keys are deliberately not configured to require authentication for every background operation. The UI lock must not be described as locking all cryptographic use.

Explicit app copy actions mark the clipboard item sensitive and schedule cleanup after 60 seconds, only if the same item is still current. Cleanup may not run if the process ends or Android restricts background clipboard access; later clipboard items are left alone. Android selected-text copying, external clipboard history, recipient apps and exported copies are outside this cleanup. No guarantee of remote recall or clipboard erasure is made.

## Existing installations and key recovery

Existing preference strings migrate in one committed preferences transaction. Schema versions 1–4 migrate transactionally into the encrypted archive schema; schema 6 adds retention metadata. Message IDs, review/saved status, public-key trust and eligible pending delivery are retained, subject to explicit discard and retention gates. SQLite secure deletion and post-commit compaction/checkpointing reduce logical plaintext remnants in database pages and journals; a committed marker retries interrupted cleanup. This cannot guarantee forensic erasure from flash storage, provider backups or copies made before the update.

There is no plaintext fallback for an unreadable encrypted value. Missing/invalid keys or corrupt encrypted data must not be interpreted as an empty archive or new family. The UI shows a recovery screen and retains existing files. Unlock the phone and retry; if storage remains unavailable, preserve the app data for diagnosis. Clearing app data, uninstalling or losing Keystore keys can make existing encrypted data unrecoverable. App cloud backup and device transfer remain disabled.

Routine remote family-key rotation remains an old-channel operation, preserving history and eligible queued delivery without renewing deadlines. It is not compromised-key recovery and does not provide forward secrecy. The separate **家長主密碼與金鑰 → 秘密可能外洩：重新安全配對** flow creates fresh family secrets and a staged Keystore signing identity, with a durable transition journal. The screen can first send the child phone a signed release and ask the relay to delete the old room, reporting whether the relay confirmed it; without confirmation the existing pairing is kept, and the parent can instead choose separately confirmed creation without purge assurance. Old archives remain isolated while old pending content and trust settings are discarded. Replacement secrets are not sent through the old channel. The child must stop old capture locally and re-pair on safe devices with full security-code verification; neither rotation, remote reset nor fresh pairing recalls copied old data.

Password inputs remain excluded from saved activity drafts. Intentional copy/share/export actions still produce plaintext for the selected recipient, outside the archive's encryption controls.

## Retention and withdrawal

New archive records are assigned 30-day deadlines by default, measured from when the parent's phone receives the record (the child's timestamp is display-only); shorter retention is supported. Ordinary saved/review flags do not bypass expiry. Record details offer explicit individual preservation for a one-time 90-day period from that action. Legacy archives keep a null expiry until a preview and explicit adoption; adoption uses the original record time and can immediately expire older records. Cleanup runs during archive preparation, receipt and record access. An assigned deadline is not evidence of immediate on-disk removal while the app is stopped.

Outboxes and incomplete assemblies have 72-hour deadlines. Existing pending rows receive a 72-hour transition deadline when schema 6 is adopted. Content-free lifetime/tombstone metadata survives acknowledgment, discard, retries and routine scope rotation to prevent the same event being requeued with a fresh deadline. On a parent whose family was paired by QR code, the nightly cleanup removes a replay identifier about 16 days after storing it (twice the 8 days in which a signed child record is accepted) unless its record is still kept; a 5.2 pairing and the child phone keep theirs. General cleanup must run to remove expired on-disk content; replay protection is not a claim of forensic erasure or detection of a newly captured copy with a different identity.

Child withdrawal persistently gates new capture and local transfer, with hold/discard choices. Explicit resume discards old pending content and clears expanded acknowledgment; saving scope choices also discards old pending content, and widening scope clears acknowledgment. Already forwarded/relay-buffered packets, delivered parent archives and external copies require separate handling. See [deletion instructions](ig-guard-data-deletion.md) and [relay retention boundaries](ig-guard-privacy-policy.md).

## Limits

Encryption protects an extracted storage snapshot when its Keystore keys remain unavailable. A compromised running app or sufficiently privileged attacker operating through the app's identity can still access data during authorised decryption. It does not provide complete device-compromise protection or make imperfect Instagram capture reliable evidence. No absolute security guarantee is made.

Robolectric uses a test-only Keystore provider; software signing helpers also support fixtures/protocol vectors. Neither establishes hardware isolation or production-device authentication behavior. Physical-device Keystore, authenticated UI, update/migration and background-delivery testing remain necessary. No build, test pass, publication or absence of defects is claimed by this documentation update. The optional scores-only mode adds a model file (Beacon, about 1.1 GB) in the child phone's app-private storage (`files/risk/`). The released app carries the model inside its package and copies it there on first start; manual import is a recovery path. The model file is a plain file checked by size and SHA-256, not sealed by the field encryption above; the stored chat text for that mode is kept in the encrypted store. Any separate model feasibility experiment is not part of the app.
